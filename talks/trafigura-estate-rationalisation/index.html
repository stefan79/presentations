Approach

Four treatments, one evidence base

Trafigura's preference

Retire

Remove dormant and unused applications, including those still renewed every year.
Evidence: no users or activity across the log retention window, licence still paid.

Consolidate

Merge overlapping use cases into fewer applications.
Evidence: shared functions, overlapping user bases, parallel data stores.

Replace

Build an AI-built internal version at a lower price point and with more control.
Evidence: small user base, simple functional footprint, business rules recovered from code and documentation. Leads into the Playbook's COTS replacement path.

Retain

Keep and optimise applications that earn their place.
Evidence: active use, cost in line with value, no viable alternative.
Savings arrive per retirement unit. A licence, server or contract ends only when its last user or dependency leaves — so contract renewal dates drive the wave plan.
This mirrors Trafigura's own preference order. Every application ends with one treatment and the evidence behind it, with a confidence rating. The replace path is where the implementation tail starts and where the Playbook takes over.
The engine

From Trafigura's data to a treatment per application

Sources
  • AppCat and CMDB exports
  • Server content and discovery
  • SSO and access logs
  • Web and application logs
  • Licence and contract records
  • AWS inventory
  • Source code, where it exists
Estate graph
  • Application → deployment → host → licence → users
  • Each source is a scanner plugin; new sources never change the core
  • Entities are stitched on declared identity keys; every link records rule, evidence and confidence
  • Low-confidence links go to a human reviewer — the RFP's human in the loop
Output per application
  • The RFP's data points: name, users, stack, version, type, functional summary
  • Usage and dormancy evidence
  • Dependencies on other applications, hosts and contracts
  • Treatment with confidence rating
  • Queryable through the UI and through MCP for AI agents
Runs on-site in Kubernetes No outbound data path Read-only access LLM off by default, or in-tenant only
The scanner is a platform any source can feed. Usage data from logs and SSO answers the dormancy and user-count questions; licence data answers cost. Everything stays inside Trafigura's network, which is exactly what their tooling principle demands. The graph and findings stay with Trafigura; the tool stays with us.

Risks

Risks we state and questions we ask

Risk
Log formats are unknown until we see samples.
Mitigation: the scanner-authoring skill turns a sample into a plugin within days; we request samples in the discovery call.
Risk
Dormancy depends on log retention.
Mitigation: combine usage logs with licence use and SSO history, and flag applications used only at quarter-end or year-end.
Risk
Purchased and SaaS software has no source code.
Mitigation: evidence comes from SSO, access logs, licences and contracts; code analysis applies only where source exists.
Risk
Security approval takes time.
Mitigation: read-only, no-egress package with a data-handling statement ready at submission; AppCat import starts before approval.

Questions for the discovery call

  1. How complete and current is the AppCat listing?
  2. Which log sources exist, and how long are they retained?
  3. Where do licence and contract data live, including renewal dates?
  4. What share of the estate is built in-house versus purchased or SaaS?
  5. What does security approval for supplier tooling involve, and how long does it take?
  6. Is a Kubernetes environment available on-site, or should we bring a sandbox?
These risks are known and manageable. The discovery call is our chance to close most of them, so we go in with these six questions.
