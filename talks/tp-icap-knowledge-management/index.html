TP ICAP — Knowledge Management

The Knowledge Base as a Repository

A practical architecture for the AI-assisted modernization playbook

Companion to the AI-Assisted Modernization Playbook v2

Knowledge base construction & operation across Phases 1–5 · harness assembly in Phase 4

The frame for the whole talk: the KB is not a wiki in the sense that provokes the client's objection. It is a structured, version-controlled, machine-validated corpus with a conversational authoring surface and a published reading surface.

The objection

The playbook treats the knowledge base as a programme asset — populated in Phase 1, validated in Phase 2, consumed for design in Phase 3, used as the agent harness in Phase 4, archived as compliance evidence in Phase 5. Everything downstream depends on it.

The doubt is not conceptual. Nobody disputes the KB matters. The question is whether a delivery team — particularly its junior members — can actually initiate one and keep it structured over a multi-month programme.

The reference case everyone has in mind: the abandoned Confluence space — enthusiastically populated in the first six weeks, contradictory by month four, ignored by month six.

That concern is usually correct about wikis as normally operated. This paper describes an architecture in which it is not.

Concede the objection openly. It is right about wikis. The entire deck is the answer to why this is not that wiki.

Two clarifications up front

Initiation ≠ structure

Conflating them makes both look harder. Initiation is solved by Phase 1 extraction pipelines — agents draft KB entries from code, schemas, artefacts; humans validate. If a junior faces an empty wiki, the pipeline failed. The genuine problem is the second: keeping the corpus consistent, findable, trustworthy as it grows and changes.

The graph is the right long-term answer — and the wrong start

Graph extraction and traversal deliver real value at portfolio scale. They also impose a modelling burden when a programme can least absorb it. The architecture defers the graph without foreclosing it — the structure a graph needs is authored from day one, in a form a later graph build can parse.

These two clarifications frame everything: we are not solving initiation (the pipeline does), and we are not building a graph yet (but we author graph-ready structure).

The shape of the answer

The knowledge base is a git repository of markdown files with structured YAML frontmatter.

Structure lives in the header; readability lives in the body; neither compromises the other. Around that core sit four mechanisms:

Skill / agent layer

Structural correctness produced by tooling, not demanded of contributors.

CI enforcement

On every PR — correctness guaranteed, not merely encouraged.

Ingestion pipeline

Builds a filterable index + embedding store on merge, exposed via MCP.

Published HTML

Stakeholders who never open git can read, review, and sign off.

One sentence carries most of the design. The four mechanisms are the rest of the talk.

Frontmatter: structure without ceremony

kb_id: auth-frontend-session
category: 2                    # business logic & domain
contexts: [identity, checkout]
layers: [frontend]
concerns: [authentication, session]
source_refs:
  - src/web/auth/SessionManager.ts:44-190
validation: sme-validated
last_reviewed: 2026-06-11
related: [auth-api-token-validation]
  • category — maps to the five KB content categories
  • contexts — binds to Phase 3 bounded contexts; drives harness assembly
  • layers / concerns — the retrieval axes
  • source_refs — traceability + staleness detector
  • validation — pending / validated / sme-validated, queryable
Controlled vocabularies are the load-bearing detail. layers, concerns, contexts draw from fixed, curator-owned lists in the repo. Anything outside them fails CI. The difference between a taxonomy and a tag cloud (auth, authn, login…).
The body is prose; the header is machine-checked. The vocabulary file is small, the enforcement is one CI check, and together they prevent the silent partial-retrieval failure of uncontrolled tags.

The splitting rule & the latent graph

The splitting rule

Failure mode: one page "Authentication" covering frontend session, API tokens, and directory integration. Three layers tags — every auth retrieval returns all of it.

Rule: if a page needs more than one layers value and content differs per layer, split it. Three single-layer leaves under a parent overview that carries no layers tag. The overview is for humans; the leaves are for agents.

Frontmatter as latent graph

The frontmatter is a graph in adjacency-list form. contexts = typed edge to a bounded-context node. source_refs = typed edge to a code artefact. related = untyped edge to another page.

Building the graph later is a parse of headers that already exist, not a re-authoring. What is deferred is multi-hop traversal — real value at portfolio scale, essentially none during a pilot.

This is the argument that defers the graph without abandoning it. Deferring multi-hop traversal costs nothing and removes a modelling burden from the phase least able to carry it.

Retrieval: filter first, rank second

How does a frontend-relevant description of authentication reach the test generator working on frontend code — rather than the twelve backend authentication pages?

① Lexical filter over frontmatter

layers ∋ 'frontend' AND concerns ∋ 'authentication'. Deterministic, auditable, reproducible. A guardrail — a backend page cannot reach a frontend generator, whatever the semantic layer does.

② Vector ranking within the set

Semantic similarity reorders an already-correct candidate set, closing vocabulary gaps — "login flow" finds a page titled "session establishment" without anyone anticipating the synonym.

Filter-then-rank takes the guarantee from the first and the recall from the second. A filter cannot be talked into a near-miss; a similarity threshold can.
The ordering matters more than either component. Lexical alone is precise but hostage to tagging discipline. Vector alone recalls but returns something plausible rather than nothing.

Retrieval is code, not judgement

The distinction that matters is not lexical vs. semantic. It is whether the context set was resolved by an algorithm or chosen by a model.

An agentic system is never deterministic — even at temperature zero. So any design depending on an agent making consistent retrieval decisions is unsound. The response is to move retrieval out of the model entirely: MCP tools with defined parameters. The agent calls kb_context(context_id, layers, concerns) and receives a set. It decides what to do, not what to read.

Reproducible

Same call, same corpus revision → same set. Holds for vectors too, if the embedding model is pinned and a model change triggers a full rebuild. Semantic retrieval isn't unrepeatable — drifting embeddings are.

Recorded

The resolved set is stored as generation evidence. Rerunning replays the recorded set rather than re-executing the query — the evidence trail survives a corpus that has since moved on.

Two paths, two tolerances. Harness path — resolves once at context entry, pins, records; a missing page fails loudly. Interactive path — a BA exploring; filter-then-rank, no pinning, a false positive costs seconds. Same corpus, same tools; what differs is whether the result is pinned and recorded.
This is the conceptual spine of the whole design and it recurs in the graph outlook: reach is fine, judgement in the retrieval path is not.

Chunking & fragment addressing

Structural chunking

Someone wrote that ## deliberately. Parse to AST, split on ##, fall back to ### over budget. Each chunk carries its heading path — Authentication > Token Refresh > Failure Modes — and inherits parent frontmatter, or filter-then-rank breaks at chunk level. Tables and code blocks are never split.

Fragment IDs

Stable addresses: kb://auth-frontend-session#p-0f3a91. IDs are content-derived (a hash of normalised text), never positional — positional IDs renumber on insertion and rot every link. A file → fragment_id → char_range sidecar lets a spec cite a paragraph and a reviewer resolve it.

Where encoders earn their place — overflow splitting (a section with no subheadings), section summaries, vocabulary-drift detection (embed vs. the concerns centroid, flag outliers), tag proposal. One constraint: encoder output is advisory, never load-bearing for the harness path.
Paragraph is the right granularity floor. Structural chunking is deterministic and reviewable; encoder-derived splits and tags are suggestions a human ratifies before they affect what a generation agent sees.

Authoring: the skill layer

The direct answer to the objection — and it inverts the premise. Contributors do not, for the most part, author raw markdown with hand-written YAML. They invoke a skill.

The skill asks the questions that determine placement and tagging, proposes vocabulary from the controlled lists, generates well-formed frontmatter, computes fragment IDs, places the file, and opens a PR. A junior does not need to have internalised the taxonomy — they answer questions about what they are documenting.

Skills are the happy path; CI is the guarantee. Someone will edit in an IDE, use a different agent, paste under deadline. If skills are the only enforcement, the architecture has reintroduced reliance on discipline with extra steps.

Every PR runs required checks: frontmatter schema · controlled vocabulary · fragment-ID + sidecar consistency · link integrity · split-rule violations. Skills make compliance easy; CI makes it true.

The repository defines its own rules — conventions, vocabularies, skills, and content in one versioned artefact. That is what makes the KB portable to the next project without a platform migration.

The curator role

What converts the architecture from a design into an operating system. A named role with hours attached:

Underestimating this role — and the CI work that supports it — is the most likely cause of failure. Both are more effort than the ingestion pipeline.
Say this plainly to the client. The technology is the easy part. The curator and CI are where programmes that skip them regress to the abandoned-wiki failure mode.

Staleness: the gap the loop misses

The improvement loop captures every review action as signal, classifies the root cause, and feeds the correction back. Applied to knowledge defects it fixes wrong entries — but it is corrective, and bounded by what the pipeline provokes.

A bounded context migrated in iteration 3 changes shared authentication behaviour. The pages describing it for a context scheduled in iteration 9 are now wrong. No review action touches them for six iterations. If the analyst doesn't notice, the wrong rule reaches a generation agent inside a harness that looks complete.

Source reference staleness

A CI job in the codebase repo checks whether source_refs ranges still resolve / content hash changed. On a hit: label needs_review, open a curator-queue entry. No judgement about correctness.

Cross-context divergence

When a spec modifies behaviour under a concerns tag shared by other contexts, flag those pages. A query over frontmatter that already exists.

Both detectors are small CI jobs feeding the same improvement loop — a knowledge-defect input, not a parallel process.

Silent drift is precisely the failure the KB exists to prevent, and it is invisible to a purely reactive loop. The fix is cheap proactive detection feeding the existing resolution path.

What was considered and rejected

A third detector — flagging pages stuck in pending across N iterations — was deliberately excluded.

It fails the criterion that separates a useful detector from noise: it has no fix. A coverage-decay hit resolves to observing that a pending page is still pending — which is what pending already means. It restates existing state as an alert.

Worse, resolution needs SME time — the scarcest resource, the one thing CI cannot manufacture. The queue fills with unactionable items and the curator learns to ignore it, degrading the queue that also carries the actionable staleness hits. A detector that trains people to dismiss its own channel is worse than none.

Detection where there is a fix; reporting where there is a judgement.
The information is still valuable — pending counts by context are rendered on the coverage view and examined at the Phase 3 readiness gate and the harness readiness check, where a human weighs gaps against SME availability.

Outlook: the graph transition

The architecture deliberately stops short of a knowledge graph. The transition is a parse, not a migration — the frontmatter is already an adjacency list. Walk the repo, emit nodes and edges, re-run on every merge. The corpus does not change. The authoring experience does not change. A second index sits alongside the lexical and vector ones, answering a class of question they cannot.

What the graph unlocks — and beyond Level 3

Filter-then-rank answers set-membership questions. It cannot answer traversal questions, because relationships between pages are only implicit in shared tag values. Traversal is what matters as a portfolio matures — transitive impact, blast radius, end-to-end evidence chains, coverage as connectivity, cross-project pattern reuse.

The playbook tops out at Level 3 — an orchestrated pipeline with human review at stage gates. The ceiling is not generation quality; it is that a pre-assembled harness bounds what an agent can see to what someone decided in advance.

A graph changes that constraint — but not by letting the agent wander. Traversal is code, not judgement. kb_neighbourhood, kb_impact, kb_evidence_path are graph queries with fixed rules. What the graph adds is not autonomy but reach: the resolvable set extends along real relationships, and an empty impact set becomes a fact, not a silence.

An agent walking a graph by its own judgement reintroduces exactly the non-determinism section 4 rules out. An agent calling a traversal tool gets a reproducible, recordable set. The remaining work is contract design — edge types, depth limits, ranking, evidence recording — engineering with known shape.

When to make the move

Three readiness signals — none appear during a pilot:

Corpus scale

Below ~1,000 pages, tag filtering answers nearly every question and a graph is overhead. Traversal earns its cost when multi-hop relationships no longer fit in a curator's head.

Vocabulary stability

The graph inherits the taxonomy. Building it while concerns still churns means rebuilding the schema alongside it. Wait until vocabulary changes are rare.

2nd / 3rd project

Cross-project queries are the ones that pay for the modelling work. A single project rarely justifies it.

Until those signals appear, the frontmatter carries the structure and the graph stays latent. Waiting costs nothing — every page authored under this discipline is a page the graph can consume unchanged.
This is the closing argument of the deferral thesis: the deferral is free because the structure is authored from day one.

Open questions — decisions for Phase 3

Vocabulary governance at portfolio scale

Some terms are genuinely shared (authentication, audit), some project-specific. The split between a portfolio vocabulary and project extensions needs an owner and a change process.

Curator continuity

The role assumes a named individual with sustained context. Handover — between or mid-project — is a real risk the architecture does not itself address.

Client authoring participation

Do client SMEs author through the skill layer, or is their input captured via interview and authored by delivery? Changes the access model, review workflow, enforcement posture — per-engagement, with contractual implications.
