The estate is the specification

Both COTS exits fail the same way by hand: discovery by interview, migration per application, testing by opinion. The Dark Factory treats the running estate as an executable spec — reconstruct what is really used, generate the replacement, prove equivalence against the old system. What gets replaced differs; the method does not.

Why generate the facade per bin

Smaller surface → smaller IP/licence exposure → smaller test surface. Not one hand-written universal clone.

Wording discipline: evidence-based equivalence to agreed tolerance, not a mathematical guarantee. Coverage metric = compatibility confidence; state it explicitly.
The IP/licence question lands here first. Answer: clients keep IBM's licensed client; the facade re-implements only wire semantics the bin needs — have the interoperability/IP position ready (validate with DB, see S11). Proof = scenario extraction from analysed client logic + recorded traffic, run against real MQ and the compat server.

MQ — steering, rollout, kill switch

Rollout is a routing problem, not a client-change problem — and every step must be reversible without touching the client.

Steering options to validate

  1. CCDT / connection-name repoint
  2. MQIPT or equivalent proxy, routing by rule — flip = cutover/fallback, no client change (licence/policy check)
  3. DNS / LB level
On z/OS, steering is coarser — queue-sharing group or QM-alias level. Call this out.

Cutover ladder

DEV → TEST (diff suite green) → STAGE (replayed prod traffic) → PROD shadow → PROD active.

Kill switch — two layers

1 · Manual re-route in seconds — drain-then-flip or flip at queue-empty; idempotent consumers preferred.

2 · Dead-man's switch — compat server stays authoritative only while observability renews the health check (message-count reconciliation, DLQ growth, latency percentiles, commit/rollback ratio, consumer lag). Missed heartbeat → auto-revert to MQ.

MQ stays warm per workload until the soak period clears, then licence retired per QM (z/OS: per MSU baseline via SCRT).
The fallback question is the second technical probe. The answer is the two-layer kill switch — especially the dead-man's switch: absence of positive health signal is itself the trigger, so a silent failure reverts rather than persists.

1 · Usage & cost ranking from SAS logs, Metadata audit, scheduler, WRS/VA access logs: frequency, last accessed, consumers, compute & licence share. Expect a long tail of dead reports → retire, not migrate. Output: ranked backlog + pilot ("amber") set.

2 · Map the solution space — every S7 node becomes an AST/dependency node (SAS parser = new JavaLens front end).

3 · Lineage slice per report — click a report, see the whole chain (loader → dataset → job → macro → report). Slice = migration unit.

4 · Target definition — declarative mapping per S7; lane per slice: straight conversion / adaptation / redesign (SME decision).

5 · Generate & provision — one action creates datasets, Dataform jobs, Composer DAGs, LookML; reuses already-migrated nodes so overlapping slices shrink.

The scope discipline is the whole argument: 186 reports, but the tail is dead. Usage-and-cost ranking decides order; lineage slicing decides the unit. Overlapping slices share migrated nodes — later waves get cheaper.

SAS — bulk migration, parallel run, user-in-the-loop

Migrate slices in bulk, run SAS and target in parallel for a short window, prove equivalence differentially, and let users close the loop directly in the new report.

Waves by lineage cluster

Component / vertical / hybrid graph cuts — migrate clusters, not files.

Parallel run = SAS as oracle

Every scheduled run compares SAS vs target (values, row counts, exceptions) to agreed tolerance. Google's mainframe Dual Run is the same idea — cite as precedent.

Appendix A1 · MQ estate — reference / methodology

MQ estate — two cost regimes, two diagnostics

Not one MQ problem: z/OS and distributed are structurally different cost regimes — different evidence, different remediation levers. Sizing comes from the platform's own accounting, not interviews. Working assumption · validate in week 1

z/OS tier — MSU / peak-timingDistributed tier — PVU·VPC / licensing hygiene
Cost driver CPU seconds consumed during the mainframe's peak billing interval (rolling 4-hr average). MSU-based — MQ's peak-window activity pushes up the whole LPAR's billing tier, not just MQ's own line item. Licensed core capacity (PVU or VPC), independent of actual usage. A server is billed at full capacity unless sub-capacity tracking is active.
What makes it expensive Timing, not volume. A queue manager processing millions of off-peak batch messages can be nearly free; modest volume landing in the 9am peak window is expensive. Licensing hygiene, not volume. Missing ILMT = full-capacity billing regardless of load. Oversized or scattered-across-hosts deployments inflate the countable core footprint.
How you find the money Pull SMF 115/116 records + SCRT/MSU reports → a ranked list, per queue manager, of exactly which workloads hit the peak billing window and how much MSU they burn. Source of truth = platform accounting. Two-step check: (1) which hosts run MQ without ILMT reporting — exposed to full-capacity billing by default; (2) which hosts are oversized/shared, where consolidating MQ + ACE + DataPower (all PVU-priced) onto fewer right-sized hosts directly shrinks the bill.
Remediation lever Target specific workloads / time windows for offload — move traffic off z/OS or shift it outside the peak interval. Target specific hosts / configuration gaps — fix ILMT coverage and consolidate footprint, largely independent of traffic patterns.
These are not two flavours of one optimization — they are structurally different problems needing different evidence and different levers. Keep the two paths distinct; do not merge them into a single "reduce MQ cost" story.
The z/OS share is the single biggest driver of both licence cost and migration difficulty. On z/OS you chase peak-window timing (SMF/SCRT); on distributed you chase licensing hygiene (ILMT coverage + consolidation). Flag clearly which parts are assumption vs known.
Appendix A2 · MQ estate — reference / methodology

MQ estate — topology & sizing sources

The diagnostic inventory behind the two-regime split: what runs where, and which platform sources we read to size it.

z/OS tier — the expensive licence tier

MQ for z/OS co-located with CICS / IMS / Db2; queue-sharing groups on the Coupling Facility; CICS–MQ & IMS bridges; COBOL/PL-I MQI callers. Priced on MSU.

Distributed tier — the backbone

MQ on AIX/Linux (± MQ Appliance); JMS via WebSphere/Liberty & Spring, C/.NET (XMS). Integration middleware is itself an MQ consumer — IIB / ACE flows, DataPower, MFT — often the biggest hidden users.

Edge cases to look for

MQ Advanced (AMS, MFT, Telemetry) · XA with Db2/Oracle · MQ Light / AMQP · cluster/CCDT routing.
